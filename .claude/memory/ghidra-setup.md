У пользователя установлена **Ghidra 12.1.2** (`C:\Tools\ghidra_12.1.2_PUBLIC`) + JDK 21 (Temurin). Скрипты разбора — в проекте: `D:\Claude\ZMU\ghidra\` (`README.md`, `run_analysis.sh`, `Zmu*.java`). Скрипты на Java, Ghidra компилирует их на лету — ставить ничего не надо.

Запуск (проверен вживую 2026-07-20):
```bash
cd D:/Claude/ZMU/ghidra
./run_analysis.sh ../image_BA.bin ../285W0027-1/Dump_D00077_OK/at28c256_1.bin ZmuRefs2.java
```
Автоанализ ~25 с → ~634 функции, ~43768 инструкций. Проект остаётся в `work/proj`, повторный прогон скриптов — с `-process bankB.bin -noanalysis` (быстро).

Карта памяти строится преСкриптом `ZmuMap.java`: банк B `0x20000000` (импорт загрузчиком), банк A `0x30000000`, **config-чип в нижнюю память `0x00000000`** (код бьёт по нему absolute-short: `lea (0x1d00).w,A1`), ОЗУ `0x10000000`/`0x40000000`, HW `0x60000000`, I/O `0xE0000000`/`0xE1000000`. Entry `0x20001040`.

**Гонять НА КАЖДОЙ прошивке отдельно.** У D00109 софт другой (банк B расходится с D00077 на 50–95% — а это код), поэтому вывод о поведении прибора, полученный на одном образе, на другой НЕ переносится. Три команды, по одной на экземпляр:
```bash
./run_analysis.sh ../image_BA.bin                          ../285W0027-1/Dump_D00077_OK/at28c256_1.bin                  ZmuRefs2.java ZmuWalk.java
./run_analysis.sh ../image_D00109_crash.bin                ../285W0027-1/Dump_D00109_crash/at28c256-1.bin               ZmuRefs2.java ZmuWalk.java
./run_analysis.sh ../285W0027-101/Dump_-101_D00636_OK/image_D00636.bin ../285W0027-101/Dump_-101_D00636_OK/at28c256_1_285W0593-5_9805.bin ZmuRefs2.java ZmuWalk.java
```

`ZmuWalk.java` — для каждой ссылки на `0x1D00` печатает 26 инструкций подряд. Именно им видно ограничение обходчика и границы проверяемых блоков (так нашлась CRC карты памяти: `lea (0x2a,A4),A0 / lea (0x9f,A4),A2`).

**Config-чип содержит КОД** (`0x0000..0x1CFF`), а не только данные — часть проверок живёт прямо в нём (`0x0BDC`, `0x16DA`, `0x16F6`, `0x17FC`). Связность этого кода заодно подтверждает, что отображение чипа в нижнюю память выбрано верно.

**Чему верить нельзя:** автоанализ покрывает не весь массив (~44000 инструкций ≈ четверть 512 КБ), поэтому «Ghidra не нашла ссылок» само по себе НЕ доказательство. Подкреплять сырым байтовым сканом константы по всему образу — он от покрытия не зависит. Именно так закрывался вопрос по [[config-copy-3f08]].

**Добавлено 2026-07-21:** `ZmuHoles.java` — проверка дыр CRC-покрытия четырьмя методами (ссылки извне, функции внутри дыр и их вызывающие, охват дизассемблера, обе таблицы векторов); `ZmuAt.java` — что реально лежит по конкретному адресу и есть ли на него ссылки. Ими закрыт вопрос по дырам — [[rom-coverage-holes]]. ⚠️ В `ZmuHoles.java` границы дыр захардкожены под `-021`; у `-018` они другие, править массив `HOLES`.

Повторный прогон без переанализа (проект уже собран):
```bash
"$GHIDRA/support/analyzeHeadless.bat" "$(cygpath -w work/proj)" ZMU \
  -process bankB.bin -noanalysis -scriptPath "$(cygpath -w .)" -postScript ZmuAt.java
```

Грабли, на которые уже наступали:
- `-deleteProject` удаляет проект после прогона → следующий `-process` падает с «Could not find project». Для повторных прогонов флаг не ставить.
- Многострочный `print()` в скрипте ломает фильтрацию лога по `grep ScriptName` — продолжения строк идут без префикса. Печатать построчно `println()`.
