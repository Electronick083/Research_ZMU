Чип AT28C256 #2 (32K x8, 32768 байт).

**История:** первая серия из 4 чтений была НЕСТАБИЛЬНОЙ (плохой контакт) — давала два образа:
- «разнообразный» (24 08 27 03 1F…)
- «повторяющийся/разреженный» (19 06…, 00 BD…)
Я ошибочно предположил, что разнообразный = настоящий. ЭТО БЫЛО НЕВЕРНО.

**После чистки контактов** пользователь перечитал — теперь **4 чтения идентичны байт-в-байт** (стабильно, воспроизводимо). Стабильный дамп даёт ПОВТОРЯЮЩИЙСЯ/РАЗРЕЖЕННЫЙ образ (на 0x40: `19 06 19 06`; на 0x100: `00 BD 00 BD`). Значит:
- **Настоящее содержимое = разреженный образ** (96% нулей, локально периодичные таблицы, 63 уник. значения, энтропия 0.43).
- «Разнообразный» образ был АРТЕФАКТОМ плохого контакта (дребезг шины подмешивал осмысленно выглядящий мусор).

Проверка на «застрявший адрес»: паттерны в разных областях разные (19 06 vs 00 BD), все A0-A14 влияют (4-8%) → адрес перебирается нормально, данные просто локально периодичны. Обрывов нет.

**Вывод: чип #2 считан достоверно. Эталон `285W0027-1\Dump_D00077_OK\at28c256_2.bin`** (папка `dump/` переименована 2026-06-09; ветка `-1` перенесена в `285W0027-1\` 2026-07-23).

## Назначение (разобрано 2026-06-09): ЭНЕРГОНЕЗАВИСИМЫЙ ЖУРНАЛ / NVM устройства
Данные только в первых ~5 КБ, дальше пусто (журнал растёт по мере событий). Структура:
- 0x0000–0x0CFF: преинициализированные таблицы дефолтных параметров / пустые слоты (`19 06`, `00 BD`, `00 0F` периодами).
- 0x0D3C: журнал событий — записи по 12 байт с BCD-меткой `YY MM DD HH MM SS` + код события. Реальные даты 2024 г.: 2024-08-27 03:17:12, 2024-08-30 14:57:05, 2024-06-10, 2024-07-14, 2024-07-15 (код `15 1E 71`).
- 0x0D78–0x0E39: вторая таблица (записи с кодом `89 60 4C` + счётчик).
- 0x0E3A: РЕЗЕРВНАЯ копия тех же 5 записей журнала (дублирование NVM).

Примечание: «разнообразный» образ из старых нестабильных чтений (`24 08 27…`) — это РЕАЛЬНЫЕ данные журнала, которые плохой контакт смещал к нулевому адресу. Стабильный дамп всё равно эталон.

## Структура журнала (разобрано 2026-06-09)
**Журналирование/wear-leveling:** NVM = снимки по 256 байт (0x100), каждый блок ≈ копия предыдущего + инкрементируемый счётчик (байт ~+0x7E). Поэтому одни и те же записи реплицируются десятки раз (код `15 1E 71` встречается 96 раз — это реплики, а не 96 событий).

**Формат записи:** `[6 байт BCD ГГ ММ ДД ЧЧ ММ СС] [3 байта КОД события] [параметр]`.
Два класса событий (КОД на смещении +6):
- `15 1E 71` (0x151E71): 5 событий, все 2024 г. (27.08, 30.08, 10.06, 14.07, 15.07).
- `89 60 4C` (0x89604C): отдельный поток, даты 2011–2013 (напр. 2013-06-21 12:51:37 + параметр), в области 0xD00 — уплотнённая сводная таблица со счётчиком-префиксом.
Хвостовой байт после кода — параметр/субкод/счётчик события.

**Семантику кодов из дампов извлечь НЕЛЬЗЯ:** их нет в прошивке (`image_BA.bin`) как констант, таблицы расшифровки не найдено. Нужна сервисная документация ZMU (fault code list) или дизассемблирование процедуры логирования. Не выдумывать значения.

**Роль в паре 28C256: #1 = identity+config («кто я»), #2 = журнал/состояние («что со мной было»).** См. [[at28c256-chip1-verified]] (там карта памяти и дескриптор софта), [[project-status]].

Урок: устойчивость (несколько совпадающих чтений) — единственный критерий истины; «осмысленность» содержимого обманчива.
