`D:\Claude\ZMU\SCRIPTS.md` — реестр всех скриптов проекта: что каждый делает, как запускать, эталонные результаты, порядок работы с новым блоком. Заведён 2026-07-20 по прямой просьбе пользователя («чтобы не забыть»).

Покрывает: `check_dump.py`, `build_image.py`, `check_rom_crc.py`, `walk_config.py`, папку `ghidra\` (раннер + 7 скриптов), `SerialPatcher\`.

`walk_config.py` (заведён 2026-07-21) — **дополнительный**, не замена: основной инструмент уровня C остаётся `check_rom_crc.py`, а этот берут, **когда основной не сработал** (не нашёл записей, странный результат, неизвестная комплектация). Ищет записи цепочки **по структуре** — по сходящейся self-CRC, а не по захардкоженному списку слотов, потому что слоты между экземплярами переставляются. Умеет сличать два config'а и отдельно показывать различия **вне** записей, которые не покрыты ничем.

**Why:** пользователь хочет один файл, куда можно заглянуть и вспомнить, чем что делается, не поднимая переписку.

**How to apply:**
- Добавил или переименовал скрипт — внеси в `SCRIPTS.md` сразу же. То же правило, что и для [[project-readme-file]].
- В `SCRIPTS.md` хранятся **эталонные результаты прогонов** (таблицы по `check_rom_crc.py` и `check_dump.py`). После любой правки скрипта прогнать на известных данных и сверить с этими таблицами — если разошлось, разбираться, а не переписывать таблицу.
- Не дублировать в память содержимое `SCRIPTS.md` — оно живёт в проекте. В памяти только этот указатель.

Разделение ролей: `ReadMe.txt` — факты по железу и открытые вопросы; `SCRIPTS.md` — инструменты; `.claude\memory\` — выводы, ошибки и то, почему решения приняты именно так.

## ⚠️ ПОРЯДОК РАБОТЫ ТЕПЕРЬ ПЯТИШАГОВЫЙ, И `REC_A` — ЭТО РЕПЕР

Решение пользователя 2026-07-21. Я предлагал встроить структурный поиск в `check_rom_crc.py` вместо захардкоженного `REC_A` — **предложение отклонено, и правильно: это была бы потеря диагностической способности.**

**Why:** при СДВИГЕ БАЙТОВ в чипе структурный поиск честно найдёт записи на новых местах и отрапортует «всё сходится» — сдвиг для него невидим, потому что self-CRC переезжает вместе с записью. Увидеть сдвиг можно только по расхождению с ФИКСИРОВАННЫМ репером. Избыточность здесь и есть диагностика. Довод пользователя, я его не учёл.

**How to apply:**
- Порядок работы с новым блоком теперь **5 шагов**: `check_dump` → `build_image` → `check_rom_crc` (основной) → `walk_config` (дополнительный) → при аномалии Ghidra. Оба инструмента гонять ВСЕГДА, не только при сбое.
- `walk_config.py` НЕ заменяет `check_rom_crc.py` и не может: он принимает только config и **вообще не смотрит на массив**. Уровень C — единственное, что ловит порчу в 512 КБ (так был найден дефект D00109).
- Различать перестановку и сдвиг: **перестановка** переставляет записи внутри того же набора смещений (штатно — так у D00092 против D00077); **сдвиг** двигает все записи на одну дельту — разбираться.
- Таблица трактовок расхождений двух инструментов — в `SCRIPTS.md`, раздел «Зачем гонять оба».
- Тот же принцип, что в [[diagnostic-design-principle]]: не выкидывать проверку, ловящую класс дефектов, ради удобства.
